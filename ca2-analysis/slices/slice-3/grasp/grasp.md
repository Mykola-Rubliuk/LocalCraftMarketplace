# GRASP justification — Slice 3

| Design decision | Pattern | Justification | Alternative rejected |
|---|---|---|---|
| `OfflineReconciliationService` receives `enterOfflineTransaction`, `reconcile` and `resolve`, and coordinates reconciliation and sale recovery | Controller | The system operations in the SSD need one use-case controller. Reconciliation is a multi-step workflow (load entry, build or reuse the SaleRequest, recover, check, record, update state) that touches several collaborators; only a controller can order these steps and guarantee that recovery happens before conflict checks. | UI handling the workflow (mixes presentation and logic); `OfflineTransaction` calling ports (the entity would depend on sale and stock services) |
| `OfflineReconciliationService` creates `OfflineTransaction`, `OfflineLine` and `SaleRequest` | Creator | It has the initialising data: the form data on entry and the entry's lines, date and reference when the request is built. Creating the SaleRequest once and storing it on the entry keeps retries identical | Building a new request on every attempt — the payload could differ and trigger `IdempotencyKeyConflict` |
| `OfflineTransaction` changes its own status (`markReconciled`, `refer`, `resolve`) | Information Expert | It knows its current status and which transitions are allowed, so the rules live in one place | Service setting fields directly — transition rules spread across the service |
| `ConflictChecker` detects duplicate references and stock conflicts | Pure Fabrication, High Cohesion | No domain concept owns both the duplicate-reference rule and the stock rules. A dedicated checker keeps all referral rules together, has no side effects and is easy to test with fakes | Checks in the controller (bloated controller); checks in `OfflineTransaction` (entity depends on the repository and stock port) |
| `OfflineTransactionRepository` handles entry retrieval and persistence | Pure Fabrication, Indirection | Storage is a technical concern. A repository gives the precise look-ups the workflow needs (`findByEntryId`, `findBySubmissionId`, `existsOtherWithRef`) and lets an in-memory fake replace real storage in tests | Static collection inside the service; selecting by `offlineRef`, which can be repeated |
| `SaleRecordingPort` isolates offline reconciliation from the sale-recording implementation | Protected Variations, Indirection, Low Coupling | Slice 3 depends only on `recordSale` and `findRecordedResult`, not on `SaleService`, `SaleRepository`, `Sale` or `SaleLine`. Sale validation, maker attribution, stock update and idempotency stay in one authoritative path owned by Slice 4; Slice 3 can be tested with a fake recorder | Slice 3 creating Sale objects or marking stock Sold itself — two sale paths and double stock updates |
| `StockAvailabilityPort` used read-only (`getStatus`) | Protected Variations, Low Coupling | Slice 3 needs only the shared stock vocabulary; stock transitions belong to the stock provider | Slice 3 changing stock |
| `Clock` injected | Protected Variations | Timestamps and the "date not in the future" check are testable with a fixed clock | Calling the system clock directly |
